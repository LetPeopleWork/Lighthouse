# 004 Compress safe\-method answers and static files at serve time
Status: Proposed

## Context

```text
On slow lines most of a page load is uncompressed JavaScript (3.4 MB raw, 1.0 MB gzipped); the server compresses nothing and the build makes no precompressed files. API answers are also uncompressed. Compressing over HTTPS risks BREACH when a body mixes a secret with attacker-reflected text.
```

## Decision

```text
Use ASP.NET Core ResponseCompression with Brotli and Gzip at Optimal level, before the static-file middleware, with EnableForHttps. A single policy class compresses only answers to GET and HEAD, with a compressible MIME type, outside the SignalR hub. Unsafe-method answers, including the one that carries a new API key, are never compressed.
```

## Alternatives

```text
MapStaticAssets with build-time compression: rejected, needs a manifest built after the frontend build and replaces the static-file path that keeps index.html uncacheable. Vite precompression plus a custom file provider: rejected, a new dependency and hand-written negotiation for about 50 ms CPU per cold load. Static files only: rejected, leaves large metrics and settings answers uncompressed. Compress everything: rejected, compresses the API-key answer.
```

## Consequences

```text
About 50 ms CPU per cold load of the whole bundle on the server; no build or Docker change; a future GET answer that carries a secret next to reflected input would be compressed, so such an endpoint must answer a POST or extend the policy. Reverse proxies that already compress keep working because an encoded answer is not encoded twice.
```
