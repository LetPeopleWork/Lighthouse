# 004 Compress safe\-method answers and static files at serve time
Status: Proposed

## Context

```text
On slow lines most of a page load is uncompressed JavaScript (3.4 MB raw, 1.0 MB gzipped); the server compresses nothing and the build makes no precompressed files. API answers are also uncompressed. Compressing over HTTPS risks BREACH when a body mixes a secret with attacker-reflected text. The Docker image serves HTTPS directly; the Helm Ingress does not compress by default.
```

## Decision

```text
Use ASP.NET Core ResponseCompression with Brotli and Gzip at CompressionLevel.Optimal, never SmallestSize, no size threshold, before the static-file middleware, with EnableForHttps. A single policy class compresses only answers to GET and HEAD with a compressible MIME type, outside excluded routes matched on path segments, case-insensitive: the SignalR hub with its negotiate route, the logs routes and the embed handshake. Unsafe-method answers, including the one that carries a new API key, are never compressed. A start-up switch ResponseCompression:Enabled, default true, turns it off (environment variable ResponseCompression__Enabled=false, restart needed).
```

## Alternatives

```text
MapStaticAssets with build-time compression: rejected, needs a manifest built after the frontend build and replaces the static-file path that keeps index.html uncacheable. Vite precompression plus a custom file provider: rejected, a new dependency and hand-written negotiation to save about 35 ms CPU per cold load. Brotli SmallestSize: rejected, about 140 times slower for a few percent fewer bytes. A size threshold: rejected, it can only act where Content-Length is known, the static files, where compression pays most. Static files only: rejected, leaves large metrics and settings answers uncompressed. Compress everything: rejected, compresses the API-key answer. Leaving compression to a reverse proxy: rejected, the Docker image serves HTTPS with nothing in front and the chart's Ingress does not compress by default.
```

## Consequences

```text
About 35 ms of server CPU per cold load of the whole bundle (measured, x86_64); no build or Docker image change. Reverse proxies that already compress keep working because an encoded answer is not encoded twice, and a proxy that strips Accept-Encoding gets identity answers; operators need no proxy compression. BREACH edge cases: the logs routes hold log text an attacker can reach next to library exception text, so they are never compressed; the embed handshake is the one GET whose body carries a token, and it is never compressed; the embed cookie is SameSite=None, so cross-site GETs carry it, and no other GET in embed scope returns a token. A future GET answer that carries a secret next to reflected input would be compressed, so such an endpoint must answer a POST or be added to the excluded routes. An identity answer to a request without Accept-Encoding has no Vary header; StaticFiles keeps one strong ETag for every encoding; application/problem+json and image/svg+xml stay uncompressed. Content-Encoding and Vary headers show it is on; no metric or alert.
```
