# ADR-237: A Test File or Class Over Its Time Budget Fails the Verify Job

**Status**: Accepted (provisional — taken while the maintainer was away; pending ratification).
**Date**: 2026-10-14
**Feature**: ADO User Story #6302 (the frontend and backend CI verify stages got slower). Follows `backend-test-speed` (ADR-074).
**Decider**: Morgan (Solution Architect), interaction mode = PROPOSE; the recommended options were taken under the maintainer's standing rule for decisions that do not change what a user sees.

---

## Context

In the first two weeks of October the frontend and backend verify jobs went from about 11 and 13 minutes to about 17 and 15. Nearly all of it was test time. A few new test files and classes each cost 30 to 115 seconds, and nobody noticed until the job durations had drifted for two weeks. A single 115 s frontend file merged on 12 October and was only found by working back from the trend.

Both jobs already write per-test timing CSVs: `vitest_to_csv.py` writes `test-timings-frontend.csv` (file, test, duration, outcome) and `trx_to_csv.py` writes `test-timings-backend.csv` (full test name, category, duration, outcome). They are uploaded as artifacts and nothing reads them automatically.

Three facts constrain any check built on them:

- The same commit runs anywhere from 0.55× to 1.13× of its typical time depending on the runner, so a limit must have about 2× headroom and still catch a real regression.
- On CI, Vitest stops at the first failure, so a red run's timing file is partial.
- The backend run includes different test classes from push to push (live-connector suites join only when a connector changed), and coverage makes CPU-bound backend tests several times slower than locally. A backend limit therefore cannot be calibrated on a developer machine, and a limit set before the fixes land would be noisy.

## Decision

1. **One script reads the CSVs.** A new `Scripts/test-timings/check_budget.py`, beside the converters, takes its column names from them. Its core is a pure function (timing rows + budget + allowlist → breaches); the script around it only reads files, prints, and sets the exit code. Developers run the same command locally against a downloaded artifact.
2. **The unit is a frontend file or a backend class**, measured as the sum of its tests' durations. A backend class is the full test name up to the last dot, after removing the argument list (arguments can contain dots, such as URLs).
3. **The budget is a fixed number of seconds per stack**, set from at least five `main` runs after the slow files are fixed. With L the largest unit not on the allowlist over those runs, the budget B is at least 2.1 × L, because the fastest and slowest runners differ by a factor of about 2.05 (1.13 / 0.55) and a unit seen at L on a fast runner must not trip the budget on a slow one. B is also at most 0.55 × the smallest regression it must catch, so that regression still trips it on the fastest runner; for the frontend, a 115 s file gives B ≤ about 63 s. If both bounds cannot hold, the units above B / 2.1 go on the allowlist with a reason and their own ceiling. The calculation is written down next to the number and in `docs/ci-learnings.md`, and is redone if the runners change.
4. **The allowlist is a checked-in JSON file**, one section per stack. Every entry carries a reason and its own ceiling in seconds, set at least 2.1 × that unit's largest observed time for the same runner-spread reason as the budget, so an accepted slow test (a container start-up, say) cannot grow without limit. A frontend entry whose file no longer appears in the timings fails the check; a backend entry is only checked for still existing in source, because the backend set varies per run.
5. **It runs as the last step of each verify job, and only after a green test run.** It cannot hide a test failure, never reads a partial file, and never stops the Sonar steps from running.
6. **Frontend breaches fail the job from the start. Backend breaches print as warnings** until at least five backend `main` runs **after the budget commit** show zero budget warnings (the largest backend unit at or under the budget on each); then one line switches them to failing. The runs the budget was derived from cannot count, because they sit under it by construction. Warn mode softens only budget breaches; a stale allowlist entry fails in both stacks.
7. **It fails closed.** A missing, empty or malformed CSV after a green run fails the step with a message naming the file. On a Python older than 3.12 the script stops at once with a message naming the version it needs.
8. **It proves itself on every run.** The step first runs the script folder's unit tests, including a planted over-budget unit, an allowlisted one and a missing file. This also puts the existing converter tests in CI for the first time.

The failure message names the file or class, its time, the budget, and the allowlist file to edit. It is written as a GitHub workflow-command annotation, with `%`, CR and LF percent-encoded so that a unit name cannot break the line or start another command.

## Alternatives considered

- **Add a budget mode to `summarise.py`.** Rejected: it reads the raw TRX and Vitest reports, not the CSVs, and exists to print a table for people. A gate inside it would mix two jobs.
- **A check inside each test suite** (a Vitest reporter, an NUnit hook). Rejected: two mechanisms in two languages, and NUnit has no clean point at which every timing is known.
- **Frontend file wall time from the Vitest report.** Rejected: needs a new column on a shared artifact, and adds the file's import and environment time, which is shared noise rather than the file's own cost.
- **A percentile of the run's own distribution.** Rejected: the bar rises as the whole suite slows, and the offending file inflates the percentile it is compared against.
- **A speed index against the run's median file.** Rejected: the median file takes milliseconds, so the ratio is noisy and the message is hard to act on.
- **Allowlist inline in the script, or as markers in test files.** Rejected: the first makes every entry an edit to the gate's code; the second needs a source scan and comments that exist only to cite a rule.
- **Backend failing from the first day, or frontend only.** Rejected: the first risks failing pushes on run-to-run noise before calibration; the second leaves the backend slow tests that started this work unwatched.
- **Skip with a warning when the CSV is missing.** Rejected: a check that passes when it has nothing to check proves nothing.

## Consequences

- **Positive**: a slow file or class fails the build on the commit that adds it, with its name and the fix (speed it up or allowlist it with a reason). No second test run; the check costs well under a second. Accepted slow tests are visible in one reviewed file, each with a reason and a ceiling.
- **Positive**: the timing scripts' own tests start running in CI, so a converter change that breaks the CSV columns is caught where it happens.
- **Negative**: the budget is a number that must be revisited if the runner fleet changes speed; the derivation has to stay next to it.
- **Negative**: until the backend switches to failing, a slow backend class only warns, and a warning can be ignored.
- **Negative**: a legitimately slow new test now needs an allowlist entry in the same change, one more file to touch.
- **Neutral**: product behaviour, API contracts and authorization are unchanged; this governs the CI test jobs only. `docs/ci-learnings.md` gains the rule: a new test file over the budget fails CI; speed it up or allowlist it with a reason.

## Amendment 2026-10-14 (provisional, pending maintainer ratification)

**Change to decision 6.** Until at least five `main` runs after the fixes are pushed exist to calibrate on, **both** stacks run the check with `--warn-only`. The first budget is a provisional one: the same formula as decision 3, with L taken from timings measured on a developer machine and from the most recent CI timings for the tests the fixes did not touch.

- **Frontend:** once those five runs exist, the budget is worked out again on them and the frontend switches to failing by deleting `--warn-only` from its step.
- **Backend:** unchanged, it follows decision 6 and switches to failing once at least five backend `main` runs after the budget commit show no budget warning.

**Why.** The fixes this budget depends on were made while the maintainer was away and nothing could be pushed, so no CI run of the fixed suites exists yet. Decision 3 asks for the budget to be set from such runs, and a developer machine runs at a different speed from the CI runners. A failing check on a number nobody has checked against CI could turn the first push red because the number is wrong, not because a test got slow. That would teach people to distrust the check before it ever caught anything. Warn mode still fails on a missing or broken timing file, a broken allowlist, a stale allowlist entry or a failing self-test, so the check is live from the first push. Only the budget comparison is softened, and only until it can be calibrated.

## Amendment 2026-10-15 (maintainer decision)

**Change to the 2026-10-14 amendment and to decision 3.** No quiet machine is available to time the fixed suites locally, so the provisional budget is derived from CI timing CSVs only. The frontend budget comes from nine `main` runs that carry the frontend fixes; the backend budget comes from eight `main` runs. Cross-checking the budget against a local full-suite run is owed, for when a quiet machine is available. The formula is unchanged.

- **Frontend:** B = 63 s, anchored on the 115 s file that started this work (0.55 × 115). Nine files are on the allowlist.
- **Backend:** B = 34 s, anchored on the 62 s that `CacheTest` took during a thread-pool stall: its barrier participants were parked on pool threads and held up every class running beside it. That stall is the regression the backend half of this work found, so the backend budget is set to catch it (0.55 × 62 = 34.1). This puts 66 classes on the allowlist. Anchoring on the frontend's 115 s instead would give B = 63 s with 27 entries, but a 63 s budget could never catch a 62 s stall.

**Consequence.** The backend allowlist is long, and every entry is checked for still existing in source (decision 4). So renaming or deleting an allowlisted backend class fails the step as a stale entry, even in warn mode, until its entry in `test-time-budget.json` is edited in the same change. About 24 of the 66 entries are there only because their largest time came from a run with the stall in it. They will drop out when the budget is derived again on runs made after the stall fix is on `main`.

**Why.** The alternative was a shorter list that could not see the one backend regression this work was about. The maintainer accepted the longer list, and the stale-entry edits it brings, on 2026-10-15.

## Amendment 2026-11-08: a fast limit per test, two ceilings on the slow tier, and limits kept in ledgers

**Where the per-file and per-class budgets stand.** Decision 6 and the 2026-10-14 amendment are superseded: since 2026-11-06 both stacks fail the build on a breach, the frontend at 54 s per file with nothing allowlisted and the backend at 34 s per class with 23 allowlisted classes. One repository variable, `LIGHTHOUSE_BUDGET_WARN_ONLY=true`, turns the budget breaches of both stacks into warnings; empty, unset or `false` enforces, and any other value stops the check as unable to judge. Everything below adds to these budgets and changes none of them.

**What is new.** Tests now carry a tier. On the frontend the tier is the file name: a `.test.tsx` renders components, any other test file does not. On the backend it is the `category` column of the timing CSV, which reads `Integration` for a test that starts a host, a database or a container. A cheap tier is held to a tight limit per test; the slow tier is held to ceilings that only go down.

| Limit | Stack | What is measured | State on 2026-11-08 |
|---|---|---|---|
| Fast limit per test | Frontend | Each test in a file that is not `.test.tsx` | **0.7 s, enforced.** Fails the build |
| Fast limit per test | Backend | Each counted test that is not `Integration` | **20.0 s, provisional.** Warns only |
| `Integration` mean ceiling | Backend | Seconds per counted `Integration` test | **0.81 s, provisional.** Warns only |
| `Integration` total ceiling | Backend | Seconds of all counted `Integration` tests | **2,780 s at 3,353 tests, provisional.** Warns only |

1. **The frontend fast limit lives in the per-test guard**, beside the 2 s that `.test.tsx` files keep, in `vitest.config.ts`. Both are multiplied by 3 on CI and on coverage runs, so the fast limit reads 2.1 s there, and the first test of a file gets 0.31 s more for the warm-up it pays. Exceptions go in `slowTests.ts`; none is listed. It was set from five green CI runs that already existed, so it had no provisional stage and has failed the build from its first push. Its switch is the guard's own, `LIGHTHOUSE_TIME_BUDGET=warn|off`, which softens every per-test limit at once. The figure: `L` = 0.890 s, the largest test outside `.test.tsx` over the five latest eligible runs, and the limit is 2.1 × `L` ÷ 3, rounded up to 0.1 s. Dividing by 3 turns a CI time into a quiet-machine limit; 2.1 is decision 3's runner spread. Only the guard knows which test ran first in its file, which shuffled runs change, so the limit could not live in `check_budget.py`.
2. **The backend limits live in `check_budget.py` and `test-time-budget.json`.** A counted row is one that passed, in a class that does not call a live work tracking system. Those connector classes are found by scanning the test source for a class-level category attribute naming one of the five connector categories that `ci_backend.yml` excludes, so a run after a connector change still gets a verdict on everything else. A test over the fast limit is named one at a time. Exceptions sit in a `fast_allowlist` keyed by class, with a reason and a ceiling, at most 10 entries, and only once the fast limit is enforced: a class may be listed only if it holds a slow test in every run the limit was read from, which fewer than five runs cannot show. The mean only goes down. The total may go up, but only by a new entry with a reason that names what grew. The run's count, sum, mean, limits and room left are printed to the log and the job summary before the verdict, so growth shows on every run.
3. **Each backend limit is a ledger**: an ordered list of entries, each with its seconds, the CI run ids it was read from, and a reason; the total also records the test count when it was set. An entry with five or more distinct run ids is enforced: it fails the build and is never edited again. At most one entry, the last, may hold fewer: it is provisional, warns on its own number, and every run prints `provisional, n of 5` for it whether breached or not. The build fails against the newest enforced entry, so a newer, lower provisional entry adds a warning and can never switch an enforced one off. Each enforced mean or fast-limit entry must be lower than the one before it, and a provisional one may not sit above them. A ledger that breaks these rules, or a ledger with any entry when the run has no counted `Integration` row at all, stops the check as unable to judge, and the warn-only switch does not soften that. `check_budget.py --previous-budget <file>` also refuses a budget file that edits, removes or moves an enforced entry of an earlier one, or raises a `fast_allowlist` ceiling; CI does not pass it yet, so for now that rule holds by review of the diff.
4. **Which runs may be read.** The unit is one job in one attempt, never a whole run: a run's own conclusion is skewed by the deploy gate and by jobs that have nothing to do with tests, and a re-run can leave two timing files under one run id. A timing file counts only if, in that attempt, the test step succeeded (`Test Backend`, or `Build Frontend (composite)`) and it has no `Failed` row. For the backend it must also be a plain run, with every connector answer in Detect Changes `false`, from after the `category` column landed. A green re-run of a red attempt counts, under the same run id, with its artifact id written down beside the derivation. A green run is never dropped for being slow: that is the noise a ceiling has to clear, and leaving it out is how a ceiling ends up inside the noise. The five runs that enforce the backend limits are counted after the last push that moves tests from the host level down to the service port in the current round of that work, because those moves shift both `Integration` figures.
5. **The recipe for an entry.** `L` is the largest value of the figure over the runs used. Fast limit: 2.1 × `L`, rounded up to 0.1 s. Mean and total: `L` × `h`, where `h` is the largest divided by the smallest value of that same figure over those runs, never less than 1.13; the mean is rounded up to 0.01 s, the total to 1 s, and the total's test count is that of the newest run. If `h` is over 1.25 the entry is not enforced: the runs disagree by more than runner noise explains, so the maintainer is asked rather than the spread capped. Raising the total is the same derivation over the last five plain runs, the red one included. Lowering either ceiling uses the same formula and applies only when the result is lower.
6. **Turning the backend limits on.** Today's entries come from two runs. The enforcing commit is owed: once five distinct eligible runs exist, it replaces each provisional entry with one carrying those five run ids and the number re-derived on them, adds any `fast_allowlist` entries, and changes nothing else, so it is one data-only commit. It goes on a quiet window with no other push running, so its first verdict is read alone. If an enforced limit then fails on trunk, read the report first: a higher count or one class far up is the pushing change's to fix; an unchanged count is a slow runner, so re-run the failed job once; red again with the count unchanged goes to the maintainer, who alone sets `LIGHTHOUSE_BUDGET_WARN_ONLY`.
7. **The frontend has no total**, as its Vitest duration swings too far between runners for a sum to compare across runs; its report prints the sum and says so. **Shares across tiers are reported, never judged.** Each job prints its own two tiers; `check_budget.py --pyramid`, given both timing files of one commit and the Playwright specs, prints the shares across all three.

**Why.** Per-file and per-class budgets catch one slow file. They do not catch a cheap tier getting a little slower everywhere, or the slow tier growing a few tests at a time, since neither puts any one file or class over its budget. A limit per test is tight enough to name a single slow unit test, and a mean that only goes down keeps the host-level tests from getting slower on average as they move. The total does not stop a feature from adding host-level tests: from the largest run seen it leaves 13 to 25 % room, several hundred tests, so it bounds drift and trips on whichever change uses the room last, which then re-derives it with a reason. A limit read from fewer than five runs only warns, because a wrong number would turn trunk red for every change pushed after it; the maintainer chose not to hold other work for the five runs, so the limits warn in the meantime rather than wait.

**Consequences.** Until the enforcing commit lands, a slow backend test or a slower `Integration` tier only warns, and a warning can be ignored. A data commit that adds an entry must stay a data commit, so the tests of the budget file assert the ledger's rules and never its numbers. One-time set-up, such as starting a host, is outside the per-test durations, so neither ceiling sees it; the host-start guards own that.
