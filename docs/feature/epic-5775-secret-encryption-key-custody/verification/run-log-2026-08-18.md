## Findings

**F-30 · `Kept in` still names a directory the key is not in, in the custody F-14 was raised about**
(A2c/C1, 2026-08-18). Slice 06a's verdict records F-14 as *"`Kept in` names the setting where
Lighthouse keeps no key"*. What shipped names the setting in the **custody sentence** —
*"put the new key first in `Encryption__Key`"* — while the `Kept in` row still renders
`keyState.keyStorePath` unconditionally (`EncryptionPanel.tsx`, the row; `EncryptionStateDto` always
carries the directory). So the panel still points a configuration-custody operator at a directory full
of key-shaped files that does **not** hold the encryption key, which is the backup trap F-14 was
written about. Either the row takes the setting name in this custody, or it says something true about
where the key came from.

**F-31 · The panel offers a move that Check secrets says is unnecessary** (C1, 2026-08-18). With a
value written by the old build under the same configured key, `readableSecretsNotOnTheActiveKey` is 1
and the **Move stored secrets** button appears, while **Check secrets** reports
`1 on the active key` — the two surfaces disagree on whether there is anything to do. The real
difference is the storage format (`LegacyCbc` → `Envelope`), which is nowhere on the screen. An
operator reading the report sees no reason to press the button the panel is offering.

**F-32 · The rotation instruction tells the operator to keep using the retired setting** (C1,
2026-08-18). Under the retired name the custody sentence renders *"put the new key first in
`EncryptionSettings__EncryptionKey`, then start Lighthouse again"* — because it echoes
`keySuppliedThrough` — while the startup banner in the same run says that setting was retired and
will stop being read. The panel should name `Encryption__Key` here, or say both and which one wins.
Related: the retirement nudge is still **banner-only**. That was the open slice-06 question and this
run answers it — an operator running as a service or a container never sees it.

**F-33 · The refusal names a setting spelled the way nobody sets it** (B2b, 2026-08-18). The message
says *"The encryption key supplied by `EncryptionSettings:EncryptionKey`…"* — the internal
configuration path — whether the value arrived from `appsettings.json` **or** from the environment
variable `EncryptionSettings__EncryptionKey`. Both were run; the text is identical. Slice 04b's own
verdict says this run must refuse *"naming `EncryptionSettings__EncryptionKey`"*, and a Docker or
Kubernetes operator will grep their compose file or manifest for the colon form and find nothing. The
same message then spells its remedy `Encryption__Key`, so one sentence carries both conventions.
`StartupBanner.cs` already does `.Replace(":", "__")` for the start-anyway setting — the same
treatment applied here fixes it.

**F-34 · On the substrate that produces the failure, removing the switch cannot be done without
re-provoking it** (D2, 2026-08-18). The re-entry path is *set the switch, start, re-enter, remove the
switch*. Removing an environment variable from a container means `docker rm` + `docker run`, which on
this substrate destroys `/app/keys` again — so the credential just typed in is unreadable on the next
start and the instance refuses. The step that ends the incident is not in the script: the key store
has to move onto the volume (`Encryption__KeyStorePath=/app/data/keys`) **before** the credential is
re-entered. Verified end to end in that order. This is documentation, not code — the switch's own
alert and `configuration.md` should say to fix the key store first, then re-enter.

**Observation · Two identical key ids in one refusal** (D2, 2026-08-18). Minted ids are date-derived
(`k-2026-08-18-01`), so a key destroyed and re-minted on the same day wears the same id. The refusal
then reads *"…the key it started on, 'k-2026-08-18-01'. They say they were written under
'k-2026-08-18-01'"*, which reads as self-contradictory. The sentence after it rescues the meaning.
Worth knowing before the ids are ever used to tell two keys apart.

**Observation · The startup line no longer carries the key id.** `WhoseKeyThisIs.AndWhereItIsKept`
renders `<one word> · <directory>` and its comment says the id is deliberately left out because a
refusal names it. That is the opposite of what F-18's own note asked for — *"shortening should come
out of the custody phrase rather than out of the id"*. Not a defect on its own; recorded because a
running instance can no longer be correlated to a key id without opening the panel.

**Observation · `Keys held` omits the published key while something is stored under it** (B2b,
2026-08-18). Before the move the chip list showed only `k-2026-08-18-01`, while the report showed the
stored value under `k-legacy-default`. The published-key alert carries the information, so nothing is
hidden from the operator — but the row that claims to list the keys something is stored under does not
list this one.

**F-35 · The reload is documented as thirty seconds and measured at seventy** (2026-08-18).
`kubernetes.md` says the pods *"check about every thirty seconds, tunable with
`encryption.keysReloadSeconds`, so no restart is needed"*. Thirty seconds is Lighthouse's half. Before
Lighthouse can re-read anything, kubelet has to project the changed Secret into the pod, which on a
default cluster takes up to its own sync period — so the operator-visible wait between writing the
Secret and the new key being active was **70 s** here, and the ceiling is higher. The behaviour is
right and the no-restart claim holds; the number sets the wrong expectation for someone watching the
screen, and the rotation section should say what the wait is actually made of.

**Observation · The key store path in the cluster is `/app/data-protection-keys`** — the container's
writable layer. With a mounted key nothing is minted, so no encryption key is lost when the pod is
replaced; what does get regenerated is the Data Protection key and `oauth-state-secret.protected`,
which only guard in-flight handshakes. Worth stating in the chart README, because the path is printed
on the startup line and looks like something that should be durable.
