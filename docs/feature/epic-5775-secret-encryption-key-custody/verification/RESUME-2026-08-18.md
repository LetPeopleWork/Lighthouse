## Job 1 — the walkthrough runs

Nine are owed, across slices 04b, 05, 05b, 06a, 06b. Three of those slices changed **startup refusal**
behaviour, which is the difference between "the tests pass" and "we know it works". The full script,
substrates and expected verdicts are in `verification/manual-walkthrough.md`; each slice brief's
**Verdict** section lists what that slice owes.

**Before starting, have ready** (from the walkthrough's own asset list):

- `v26.8.14.1` as standalone installer, server binary, and `ghcr.io/letpeoplework/lighthouse:26.8.14.1`
  — the upgrade groups must start from the real old build, never a hand-made database. The image is
  already pulled locally.
- This branch built as standalone app, server binary and a container image tagged so nothing
  accidentally pulls `latest`.
- **One real work-tracking credential** — must come from the maintainer. It is what proves decrypt →
  HTTP end to end rather than store-and-read.
- A Postgres instance, and **a fresh scratch directory per run**. Never reuse one: a stale `keys/`
  folder invalidates a run silently.

**Grade four surfaces every run, including the boring ones**: the startup banner line and any warning
under it; the encryption panel (key source, active key, keys held, kept-in, custody sentence, which of
Rotate / Move / Check are offered); the docs an operator would have open; and the failure text of any
refusal — a remedy that does not work verbatim is the highest kind of finding.

**What can be driven without the maintainer**: the server-binary runs, both Docker groups, Postgres, and
the durability pair (D1, D2). **What cannot**: the standalone/Tauri runs (A1, B1, C3) need the desktop
app installed, and every run that proves a credential still works needs the real credential.

**Already done on 2026-08-17, do not repeat**: the live Docker+Postgres repair, which is written up as
F-28 and F-29 in the walkthrough. That instance is now on `Encryption__KeyStorePath: /app/data/keys`
and its two legacy credentials were still on the published key at the end of the session — moving them
is a one-click check once the fixed build reaches it.
