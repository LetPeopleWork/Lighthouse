# S3 id table: host rows that leave and the unit rows that prove their rules

Slice base: d7326c838. Breaks: `s3_breaks.py` (ids A1 to A40), observed output in `s3-break-evidence.txt`; the row names under each break id there are the rows that turned red. Row numbers are those of section 7.3 and the Slice03 part of 7.6 of the screen (`docs/feature/story-6537-t10-backend-rules-at-unit-level/evidence/step2/screen.md`).

The oracle (`s3_compare_ids.py`) holds the host rows that stay (Slice04 rows 1 and 17, Slice03 row 1) and every unit row, plus three rows that already exist in other classes and are named below: two in `WorkItemServiceTest` (the once-per-refresh collapse, Portfolio and Team) and one in `WorkTrackingSystemConnectionsControllerTest` (a failed connection check is answered 400). Before craft it reports the 40 host rows below as EXTRA (observed 98, expected 58): the craft removes them.

Every unit row lands in `Lighthouse.Backend.Tests/Services/Implementation/WorkTrackingConnectors/AzureDevOps/AzureDevOpsNamedRelationEndTest.cs`, which carries no live-connector category and runs the real `AzureDevOpsWorkTrackingConnector` over a mocked `WorkItemTrackingHttpClient` (the connector's own decisions run; only the HTTP client answers are stubbed). One row stays in `TeamUpdaterTest.cs`. Row names below are abbreviated by their method name in that class.

Two rules are proven once for all rows and are not repeated per row. Once per refresh: the refresh keeps one finding per kind, setting and name and writes one warning line for it, however many work items carry it. The refresh code is `WorkItemService` and is shared by Portfolio and Team: `WorkItemServiceTest.UpdateFeaturesForPortfolio_FullRefreshWhereSeveralFeaturesLackTheNamedLink_RecordsOneFindingAndOneWarning` and, for a Team, `WorkItemServiceTest.UpdateWorkItemsForTeam_FullRefreshWhereARecordCarriesAFinding_ReportsItOnceUnderTheTeamsName` (both already there: several work items carrying one finding give one finding and one warning line per refresh); break A37 drops the collapse (both rows red) and A38 writes each warning twice (both red). Refusal: every refusal row of `AzureDevOpsNamedRelationEndTest` asserts that its `IsValid` is false as well as its code or message; break A39 makes a refused check report valid (the refusal rows and the controller row below turn red). The verdict becomes a 400 on the route in `WorkTrackingSystemConnectionsController`, pinned by the existing `WorkTrackingSystemConnectionsControllerTest.ValidateConnection_DetailedValidationFailure_ReturnsBadRequestWithMessage` (status 400 with the verdict as body); break A40 answers a failed check with success and turns it red. So the refusal rows of Slice03 are proven by the unit row for the verdict and the controller row for the 400, and the kept Slice03 wire row stays the success path.
