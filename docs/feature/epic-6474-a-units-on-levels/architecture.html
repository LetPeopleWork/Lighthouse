Paradigm

object_oriented

Shared records

Decisions

D1

Paradigm object_oriented (CLAUDE.md, ports and adapters). Organisation set-up owns structure, levels, connection mappings and units inside Modules/OrganisationSetup (created by S03i); no new module.

D2

Kept ADR-273 decisions 1-3: a unit is identified by its level and its number on that level; level 1 continues Team numbers, level 2 Portfolio numbers; the five stored discriminators (OwnerType, PermissionScopeType, ReportOwnerKind, RefreshType, UpdateType) are read as the level key and never rewritten. Placement follows the two module rules: Organisation set-up's Domain reaches only its own Domain, Models and the base library, and a Contracts type reaches only the kernel, the base library, Microsoft.Extensions and other Contracts. So the Domain owns LevelId and TermPair (Domain/Structure), and the published Contracts carry the level as the stored key string: UnitId(string Level, int Number) with UnitId.ForTeam and UnitId.ForPortfolio, the views with primitive fields. The Application query maps Domain to Contracts. Rejected: putting LevelId and UnitId in the Models kernel (the kernel only holds types two or more contexts own together, and S04b just shrank it); Contracts carrying Domain types (forbidden for Contracts by ContextContractsArchUnitTest).

D3

OrganisationStructure (aggregate root, Modules/OrganisationSetup/Domain/Structure) holds exactly two Level entities: stable LevelId, ordinal (1 = where the work is done), unit name and item name, each singular and plural. It owns the rename rule and the exactly-two-levels rule for feature A. Replaced: no item types on a level (vision 2026-11-06) and no on/off switch or IsSwitchedOff column (2026-11-27: slice 15 removes level 2 instead, decided in feature C).

D4

ConnectionMapping (aggregate root per connection, Modules/OrganisationSetup/Domain/Mapping) lists per LevelId the item types of that connection, once per level ignoring case, in its own spelling. A type may sit on both levels of one connection (2026-11-27; MD6/VR3 dropped, no level wins); the overlap is recorded for the upgrade notice of feature C and blocks nothing. A connection with no mapping row (added after the upgrade, by the previous release or by an import) gets one with today's create defaults (level 1 User Story, Bug; level 2 Epic; nothing on a connector without types) the first time it is needed: IConnectionMappingStore.ForConnection creates it inside the transaction of the first Resolve, the first unit create on that connection, or the start that re-derives a unit on it. It is never derived from units' types after the first upgrade (VR8, ADR-274 rules 8 and 13). ConnectionMapping.Resolve(levelId, requested) is the single decider of a unit's subset: returns MappedSubset (mapping spelling, order of the mapping) or TypeNotMapped(type, level, connection).

D5

Persistence (ADR-275, revised): Team and Portfolio keep their tables, ids and sequences; WorkTrackingSystemOptionsOwner keeps its name (the rename to Unit is moved out: no promised observation reads it). New additive tables OrganisationStructures (fixed key 1, concurrency token), Levels, ConnectionMappings, ConnectionLevelMappings (connection id, level id, item types stored as units store lists); new columns ItemTypeSubset, NeedsItemTypes, WorkItemTypesAsWritten on Teams and Portfolios (slice 04); new table LeafCapacities keyed by Team id with cascading FK (slice 07). Generated by Lighthouse.Backend/Create-Migration.ps1 for SQLite and Postgres; HistoricalSchemaPatch learns every new table and column.

D6

Startup migrator (ADR-275 decision 4, kept): OrganisationStructureMigrator implements ISeeder; its entry is ISeeder.Seed (Task Seed()), registered after TerminologySeeder in Program.cs. Its first-upgrade step runs only when no structure row exists: it reads Teams, Portfolios and the eight Terminology rows, asks the pure OrganisationStructureMigrationPlan.From (return-only) for levels, the mappings of connections that have units, and subsets, applies it in one transaction, then checks its own result (each unit's subset within its connection's level list, no unit gained or lost a type ignoring case, unit counts unchanged); a failed check rolls back and stops the start with a structured fatal message. Later starts only re-derive the subsets the previous release edited; a connection without a mapping row then gets the create defaults as in D4, never a mapping from its units. Case is folded in C# with StringComparer.OrdinalIgnoreCase, never in SQL. A second instance loses on the fixed structure key and re-reads. Replaced: the Feature-level-wins rule, the self-check one-level-per-type and the upgrade lost-type record (2026-11-27).

D7

Rollback detection (new, corrects ADR-274 rule 13): every save that writes ItemTypeSubset also writes the effective list into WorkItemTypes and the same list into WorkItemTypesAsWritten (a unit marked NeedsItemTypes keeps its last list in both). At each start a unit whose WorkItemTypes differs from WorkItemTypesAsWritten was edited by the previous release and only that unit is re-derived (old list intersected with its connection's level list). Comparing WorkItemTypes with the subset instead was refuted: it re-ticks a removed and re-added type for a marked unit, against M2.

D8

Domain events (ADR-273 decision 6, kept for feature A): UnitCreated(UnitId) and UnitDeleted(UnitId, UnitsThatReferencedIt) are published after commit by Organisation set-up through the existing IDomainEventDispatcher (ADR-027) and live in Modules/OrganisationSetup/Contracts. TeamDeleted and PortfolioDeleted are replaced: their three handlers (TeamDeletedRefreshLogCleanupHandler, TeamDeletedForecastRetriggerHandler, PortfolioDeletedOrphanedFeatureCleanupHandler) re-subscribe to UnitDeleted in place, filtering on the level they handle, in today's order pinned by DomainEventHandlerOrderPinTest. LevelRenamed and ConnectionItemTypesChanged are named but not built in feature A (no consumer until features C and D).

D9

Terminology split (slice 02): the eight entries team, teams, portfolio, portfolios, workItem, workItems, feature, features are read from and written to the two Levels by TerminologyService; the other Terminology rows stay where they are. The old eight rows are kept (expand-only) and dual-written so the previous release shows the same words after a rollback. PUT /terminology keeps today's Premium and System Admin guard (level rename stays Premium: 2026-11-27 reverses M7).

D10

Cross-layer algebra. Domain: states = OrganisationStructure(two levels), ConnectionMapping(level -> type list), Unit(subset, needs-item-types mark); operations = Plan, Resolve, Rename, CreateUnit, DeleteUnit; observations = level names, mapped types per level, a unit's effective types, refusal reason. Application: outcomes Saved, TypeNotMapped (400), UnitNeedsItemTypes (409), Conflict (409 concurrency, unchanged). Adapter: EF stores, controllers translating outcomes to ProblemDetails codes team-item-type-not-on-level, portfolio-item-type-not-on-level, unit-needs-item-types. Infrastructure: startup migrator commit-or-stop, fixed-key race, rollback re-derivation, process crash before commit.

D11

Formal verification: Quint 0.33.1 models the startup migrator protocol (two instances racing, crash before commit, previous-release edit after rollback, admin remove then re-add) in docs/feature/epic-6474-one-structure/design/models/organisation_structure_migrator.qnt; quint run (4000 samples, 10 steps) and quint verify (Apalache, 6 steps) found no violation of its six invariants, and each invariant was broken by its own mutant. Not modelled, checked by property and example tests instead: majority spelling, tie-break and order of the planner (pure function laws), the 400 and 409 decisions (finite outcomes, no shared state), LeafCapacity copy (same commit-or-skip pattern, no new window). TLA+/TLC and Agda not needed: no fairness-dependent claim, no type-level proof. Liveness: no liveness claim, the migrator is one synchronous startup step that commits or stops the start.

D12

Examine proof: each slice's oracle lives in Lighthouse.Backend.Tests/Acceptance/OneStructure/ and is shown by the public command backend-tests with a slice fragment (for example backend-tests Acceptance.OneStructure.NumbersStayTheSame); forecast-answers-compare and metrics-answers-compare between af209fdfe and HEAD show the unchanged numbers on demo data; architecture-rules OrganisationSetup shows the boundary rules.

D13

Kept as decided: no usage-data event in feature A (all slices invisible); an item maps to exactly one owning unit of its level (2026-11-24) is not built now; connector port fetching generically per unit stays a candidate for slice 12 (owner maintainer); whether a re-added level 2 gets seeded or last names stays open for slice 15 (owner maintainer).

D14

LevelId is the stored level key, not a database number: public readonly record struct LevelId(string Key) in Modules/OrganisationSetup/Domain/Structure, with LevelId.Team ("Team") and LevelId.Portfolio ("Portfolio"), the values the five stored discriminators hold (ADR-273 decision 2). It is stable and distinct from the ordinal; a level added later (#6455) gets a new key. Contracts carry the same key as a string; a unit test pins that LevelId.Team.Key equals UnitId.ForTeam(1).Level, so the literal cannot drift between the two. Outcome sums are closed abstract records with nested sealed cases and a private constructor (as ForecastRunOutcome does); aggregate and planner constructors are internal, built through their static factories.

D15

A compile-safe RED in C#: each slice starts with a prefactoring step that adds the public signatures its oracle names (types, interfaces, members, the DI registration extension) with no behaviour: an empty answer where one is safe, NotImplementedException otherwise. The oracle then compiles and fails on its assertions. The signatures are declared per slice as constructor records and named file by file in the slice's prefactoring move.

D16

Test composition: every new service is registered by a module extension that Program.cs and the tests both call: OrganisationSetupModule.AddOrganisationSetup (existing; gains IUnitLifecycle in S3 and IUnitSettings in S4), OrganisationSetupModule.AddOrganisationStructure (new in S2: IOrganisationStructureStore, IConnectionMappingStore, IOrganisationStructureQuery, and OrganisationStructureMigrator as an ISeeder; Program.cs calls it right after registering TerminologySeeder) and ForecastingModule.AddLeafCapacity (new in S5: ILeafCapacityStore, and LeafCapacitySeeder as an ISeeder after the structure migrator). A port scenario passes services => services.AddOrganisationSetup().AddOrganisationStructure() (plus TerminologySeeder and AddLeafCapacity where needed) to ServicePortHarness and runs the resolved ISeeder instances in registration order. The Postgres scenarios build LighthouseAppContext on SharedPostgresContainer's connection string and register the same extensions.

D17

Organisation set-up's Application never reaches a context that builds on it (OrganisationSetupModuleBoundariesArchUnitTest), so the Team settings save does not call Forecasting. The API layer composes the two owners on the request's scoped LighthouseAppContext. Update: TeamController stages the capacity with ILeafCapacityStore.Stage(UnitId, LeafCapacityValues) and then calls IUnitSettings.SaveTeam. Create: TeamsController stages it with ILeafCapacityStore.StageForNewTeam(Team, LeafCapacityValues) on the Team entity the create builds, before its id exists; the store adds a LeafCapacities row whose Team navigation points at that entity, so EF keys the row to the database-generated Team id in the same SaveChanges. One commit, made by IUnitSettings (SaveTeam or CreateTeam), writes both or neither under the Team's concurrency token. A refused save (400, 409, not found, concurrency) never calls SaveChanges, so the staged row is dropped when the request scope disposes the context. Reads: the controller reads the Team through IUnitSettings.ReadTeamSettings and the capacity through ILeafCapacityStore.ForTeam, and maps both to TeamSettingDto through API.Helpers; every Team has a row, from the seeder for existing Teams and from StageForNewTeam for new ones.
