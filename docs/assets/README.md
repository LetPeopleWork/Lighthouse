# docs/assets — read before deleting anything here

Files under `docs/assets/` are **not** only consumed by the docs in this repo.

## The marketing website hot-links these files from `main`

`letpeople.work` builds image URLs with `lighthouseAsset()`
(`src/lib/lighthouseAsset.ts` in the website repo), which resolves to:

```
https://cdn.jsdelivr.net/gh/LetPeopleWork/Lighthouse@main/docs/assets/<path>
```

There is no build step, no vendored copy, and no reference to the website
anywhere in this repo — so an asset can look completely unused here (no `.md`
embeds it, nothing imports it) while a live page depends on it. Deleting or
renaming it breaks that page as soon as the jsDelivr cache for `@main` expires.

**Before removing or renaming an asset, grep the website repo:**

```
grep -rn "<asset-name>" /path/to/website/src
```

At the time of writing the website consumes: `concepts/azuredevops_team_wizard.png`,
`concepts/worktrackingsystem_AzureDevOps.png`, `features/metrics/metricsoverview.png`,
`features/metrics/portfoliometricsoverview.png`, `features/portfoliodetail.png`,
`features/teamdetail.png`. Treat that list as a hint, not as truth — re-grep.

## Generated vs. hand-maintained

Most assets are regenerated by the `@screenshot` Playwright specs. A few are
hand-maintained and have no generator: `concepts/azuredevops_wizard.png` and
`concepts/azuredevops_team_wizard.png`. The latter used to be written by
`ado.spec.ts`, which now binds a small fixture board (`DummyProject`) for speed
— regenerating it from there would have replaced a marketing image with a
screenshot of a dummy project, so the generation was dropped and the image kept.
Re-shoot it by hand from a representative board if the wizard UI changes.
