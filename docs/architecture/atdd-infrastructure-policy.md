# ATDD Infrastructure Policy

Per `nw-distill` § Project Infrastructure Policy. One file per project. Apply-if-exists; write-if-absent; rewrite with `--policy=fresh`. Git history is the audit trail.

Bootstrapped during the `time-in-state-and-staleness` slice-03 DISTILL run (2026-05-25). This is a C#/.NET backend (`net10.0`) + React/TypeScript frontend + Playwright E2E project — NOT the Python/Hypothesis pilot. The Python-pilot artifacts (`tests/common/state_delta.<ext>`, `assert_state_delta` Universe assertions, Hypothesis/PBT harnesses, `__SCAFFOLD__` stubs) do NOT apply here; the C#/TS rows of the polyglot matrix govern (NUnit `[Ignore]` and Playwright `test.fixme` are the skip markers; backend ATs are black-box example-based via `WebApplicationFactory<Program>`). The mechanisms below were already encoded as precedent across slices 01–02 and are recorded here for the audit trail.

| Production React app (E2E) | Playwright against a locally-started app, Page Object Model only | No inline `page.locator` in specs. POMs in `tests/models/`. |
| Repository-invariant checks (`.github/scripts/*.mjs`) | `node:test` via the existing `Verify Workflow Scripts` job (`node --test .github/scripts/*.test.mjs`). The check is an exported function called directly: once against the real repository root for the end-state assertion, and once per seeded violation against a throwaway tree written to `mkdtemp` | Appended during `story-6070-toolchain-single-source` DISTILL (2026-09-25), following the precedent `generate-version.test.mjs` set. No `package.json` lives under `.github/scripts`, so these checks take no dependencies: YAML and Dockerfiles are read line by line, not parsed. The skip marker is `test(name, { skip: 'pending: …' }, fn)`. The real-repository assertion cannot be green at hand-off, because the repository *is* the thing being changed; the seeded-tree cases carry the behaviour. |
| React component tree (frontend ATs) | Vitest + React Testing Library, colocated `*.test.tsx`, rendered through the real component under test with `TerminologyContext` provided | No shallow rendering, no component mocking. | Helm chart operator commands (`helm install` / `upgrade` / `rollback`, and `helm template \| kubectl apply` for GitOps) | The real Helm CLI and `kubectl` against a throwaway kind cluster, driven by bash harness scripts under `chart/tests/<concern>/` that take the cluster name as an argument; render-only claims go through helm-unittest suites in `chart/tests/unit/` instead | Appended during `story-6131-chart-postgres-major-upgrade` DISTILL (2026-10-02), recording the precedent `ci_chart.yml`'s `install-smoke` job and the `chart/tests/acceptance/*.feature` files already set. | `lh` run as one process, and the local and shared MCP servers (lighthouse-clients) | Vitest. `lh` through `runCliSession(args, io, { env, terminal, now })`, the production composition with the process's environment, terminal and clock handed in; the local MCP server through `createLocalLighthouseMcpServer(env)` connected to an SDK `Client` over `InMemoryTransport.createLinkedPair()`; the shared server through the existing `runMcpHttpRuntime` on a real port. `HOME`, `CI` and `DO_NOT_TRACK` are always set explicitly, and every file a scenario writes lives under an `aTempDirectory` home | Appended during `story-6193-usage-data-from-clients` DISTILL (2026-10-08). Whether `lh` asks a question depends on the three terminals, `CI` and `DO_NOT_TRACK`, so a test that inherits the runner's environment answers a different question on a laptop than in CI. The skip marker is `it.skip` / `it.skip.each`; the two entry points are RED scaffolds that throw until DELIVER. |
| The skills an assistant reads (lighthouse-clients `skills/`) | Two mechanisms, because only one of them can run without a model. **Deterministic, in `pnpm test`**: `skills/skills.drift.test.ts` reads what exists the way a user meets it - `createMcpCoreRuntime(...).listTools()` and the help `runCliCommand` prints - and holds every skill's Markdown to it; `skills/skills.evals.test.ts` reads every eval case and fixture. **Model in the loop, by hand before a release**: each skill's `evals/cases.json` run three times per case against `scripts/eval-fixture.mjs`, scored from the transcript and the fixture server's request log | Appended during `story-6217-lighthouse-skills` DISTILL (2026-10-08). A skill is text, so its own acceptance test is the eval case; what a test can hold on every commit is that the text names only tools and commands that exist, and that the cases can still be run as written. Cases written before their skill's folder exists wait in `test-support/pending-skill-evals/<skill>/`, because the packer refuses a skill folder without a `SKILL.md`. |
| CI timing scripts (`Scripts/test-timings/*.py`, e.g. `check_budget.py`) | stdlib `unittest` under `Scripts/test-timings/tests/`, invoking the script as a **subprocess** with `sys.executable` against real CSV, JSON and C# source files written to a `tempfile.TemporaryDirectory`; exit code and stdout (`::error::` / `::warning::` annotation lines) are the observables. Converter-to-check seams run the real converter first | Appended during `story-6302-ci-test-time` DISTILL (2026-10-14). The command line is what CI and a developer type, so a test that called the core function would miss argument parsing, file reading and the exit code, which are where a gate fails open. Python 3.12 stdlib only (the runner's interpreter); no pytest, no Hypothesis. Skip marker is `@unittest.skip("pending — …")`; the scaffold raises `AssertionError`, which a subprocess reports as exit 1 with the message on stderr, so every test also asserts on stdout to stay red against it. Run with `python3 -m unittest discover -s Scripts/test-timings/tests`. |

| `IUsageDataConsentRepository` (one row per browser, keyed by token digest) | `Testcontainers.PostgreSql` — one container per test class, fresh DB; `[Category("requires-docker")]` | Appended during `epic-5733-opt-in-usage-data` DISTILL (2026-09-11), decided by the product owner. | Seeded demo data (E2E) | `loadDemoScenario(request, scenarioId)` + `waitForBackgroundUpdates(request)` (POST `/api/latest/demo/scenarios/{id}/load`) | Deterministic seeded teams/portfolios/items with known states. | `IFeatureOrdering` (Feature order, owned by epic #5375) | Real implementation via the test factory — **never mocked** | Appended during `epic-4365-dependencies` DISTILL (2026-08-17). The dependency warnings READ the total order to spot a blocker positioned below its dependent, and assert that nothing was reordered. Substituting the ordering would make "and Lighthouse has moved nothing" vacuous. Read-only in that epic; the writer stays epic #5375's. |
| `IForecastService` + `IRandomNumberService` — **real**, seed pinned (epic-boundary gold tests only) | Real Monte Carlo run against a fixed `IRandomNumberService` seed, executed twice: once with dependency data absent, once with it present, asserting every percentile identical | Appended during `epic-4365-dependencies` DISTILL (2026-08-17). This is the deliberate exception to the `Mock<IForecastService>` row below. A mocked forecast cannot prove "this epic moves no date" — the claim is precisely that the real simulation produces byte-identical output, so the simulation has to run. Confine to the `epic-boundary` scenarios; every other test in the epic keeps the mock. |
| `IUpdateStatusStore` (the record of which updates are in flight) — **real**, never mocked | Real store through the real `UpdateQueueService`: `InProcessUpdateStatusStore` by default, `RedisUpdateStatusStore` via `Testcontainers.Redis` under `[Category("requires-docker")]` for the shared-store scenario | Appended during `epic-5792-dependency-aware-forecasting` DISTILL (2026-08-21). Slice 00 debounces a forecast trigger behind the sibling Teams still queued, so "the trigger was parked" has to be a statement about the queue rather than about a mock. The Redis adapter runs only where Redis is configured, which is exactly why it needs a container rather than an assumption. |
| `IDomainEventDispatcher` + its registered handlers — **real**, never mocked | Real in-process dispatcher through the test factory; the observable is whatever the shipped handler drives | Appended during `story-5876-behaviour-settings` DISTILL (2026-08-31). "The policy change was published" is a claim about the fan-out reaching its handler, not about a call on a bus. Asserting it against a `Mock<IDomainEventDispatcher>` would keep passing after a handler is unregistered, which is the failure worth catching. |
| `IUsageDataEventQueue` (what an accepted batch waits in) + the hosted service that empties it — **real**, never mocked | Real queue through the real host. **The integration host removes every `IHostedService`**, so the drain does not run there: the scenario has to pull a trigger on the seam the controller writes to. Polling the outbound recorder is the fallback and costs every negative scenario its full budget | Appended during `epic-5733-opt-in-usage-data` DISTILL (2026-09-12, slice 01c). "The next event after a withdrawal did not happen" is a claim about what left the instance, and the check runs a second time on the way out of the queue — so a mocked queue would assert the accept half and silently drop the half that catches a withdrawal landing mid-flight. Nothing on this path is persisted, deliberately: a durable queue survives the withdrawal it is meant to obey. |
| Bundled Postgres data volume (Helm chart) — **real**, never simulated | The StatefulSet's own PVC on a throwaway kind cluster: the local-path default storage for most scenarios, and a static `PersistentVolume` on a size-limited tmpfs inside the kind node (`claimRef` to the StatefulSet's claim) where the scenario needs a full volume. Proof that nothing was written is a sorted `sha256sum` listing of the volume taken from a debug pod before and after | Appended during `story-6131-chart-postgres-major-upgrade` DISTILL (2026-10-02). The local-path provisioner ignores the requested size and `df` reports the node's disk, so a small PVC there still looks roomy; only the tmpfs makes "too little room" real. Container images (`postgres:16`, `postgres:17-trixie`, `postgres:18-trixie`, the released API image) are real too, pre-pulled on the runner and loaded with `kind load docker-image`. No external fake exists in chart work. |
| Stored report rows (`Reports` table, its JSON payload) as another version of Lighthouse would have written them | Real EF through the test host, then parameterised SQL on that host's own connection to change one row: its type key, a payload member it carries, or a metric capture it lacks | Appended during `epic-5878-baseline` DISTILL (2026-10-13). The forward-tolerance rules (a report of a type this version does not know is listed and deletable but not opened; an extra payload member is ignored) and "a metric the report never captured cannot be shown" are about rows the API under test refuses to write, so no driving port can produce them. Only the row is reshaped; everything that reads it is production. |
| `IConnectionSaveService` (the connection save: opened, then committed) — **real**, decorated only to open a gap | The production service through the test host. Where a scenario needs another save to land between opening and committing, the harness re-registers the shipped implementation under its own type and puts `ASaveLandsInTheGap` in front of it, which runs the other save just before delegating `Commit`. Without a registered implementation the decorator is not applied and the scenario fails on its assertion | Appended during `epic-6303-configure-once-per-connection` DISTILL (2026-10-16). "A Team that started using a field while its removal was being saved still blocks it" is a claim about a race, and the only deterministic way to stage it is to choose the moment. The gap is the one the design names: owners are looked up when the save commits, not when it was opened. |
| An upgrade of a database written by the previous release (both providers) | A real SQLite file and `PostgresContainerFixture.StartFreshAsync()`; `IMigrator.MigrateAsync(<previous id>)`, owners written with **today's** model (with `HistoricalSchemaPatch` around the write), then `MigrateAsync()`; the new columns read with raw SQL, the fingerprints recomputed with `FetchFingerprint.For` on an EF reload | Appended during `epic-6303-configure-once-per-connection` DISTILL (2026-10-16), recording the `BlockedRuleSetMigrationTests` precedent for the source columns. The back-fill is data the API cannot write (a value naming a field that was deleted, or another connection's field), so it has to be seeded below the API. Like every class in `Integration/Containers`, it carries no `Integration` category and runs in the filtered suite, which needs Docker locally. When DELIVER changes the model, the seeding's property setters are where the compiler points first. |
| The update-stop broadcast between replicas (Redis pub/sub, the stop-everything message) | `RedisContainerFixture` (real Redis in Testcontainers), two production `UpdateQueueService` instances standing in for two pods, each on its own connection; one waits on its own update's stop, the other is asked to stop everything | Appended during `epic-6311-responsive-during-updates` DISTILL (2026-10-18). "A click on one replica stops work running on another" is a claim about a message crossing a real broker, and the in-process notifier delivers in the same process, so it would pass with no broadcast at all. Redis there is a proof of concept, so the class holds one simple scenario and nothing more. Runs in the filtered suite and needs Docker, like every class in `Integration/Containers`. |

Faking it turns "the change re-queues the forecasts" into something a test can see the moment the write commits — and it is the observable the real `IDomainEventDispatcher` row above is read through. |
| `IUsageDataPublisher` (the outbound call to the PostHog capture API) | A capturing fake registered in place of `PostHogUsageDataPublisher`, recording every payload it was handed | Appended during `epic-5733-opt-in-usage-data` DISTILL (2026-09-11). Emit is fire-and-forget and degrades silently by specification, so a real call would make "nothing was sent" indistinguishable from "the vendor was down". The fake is what turns the payload-purity and revocation-latency invariants into assertions. **A test may never let the real publisher resolve**: the collector host default is production, and a leaked emit lands in the census. The separate zero-leak assertion is the inverse — a `DelegatingHandler` over the named clients proving no request reaches the collector host at all when no browser has consented. |
| Every outbound HTTP request the application makes (the zero-leak observation) | `CapturedOutboundRequests` + `OutboundRequestRecordingFilter`, an `IHttpMessageHandlerBuilderFilter` registered on the test host. It sits in front of **every** client the framework hands out, records address and body, and answers locally so no test reaches a real network | Appended during `epic-5733-opt-in-usage-data` DISTILL (2026-09-12, slice 01c). A capturing fake publisher only proves the publisher was not called; this proves nothing left, whatever asked. It is exactly as complete as the rule that nothing on this path builds its own `HttpClient` — several elsewhere in this codebase already do, which is why the rule is scoped to the usage data path and why `UsageDataEmitSeamArchUnitTest` carries it. Without that rule the assertion decays into a tautology, so the two ship together or neither is worth having. |
| `IDrawStreamFactory` (where the feature forecast gets its random numbers) | `DrawsTheSameNumberEveryTime` when the claim is about *which day*; `DrawsFromAPinnedStartingNumber(seed)` when the claim needs a real spread. Registered by `RemoveAll` + `AddSingleton` in the factory builder, alongside a reduced `ForecastSimulationLimits` (50 runs deterministic, 1 000 sampled, against the product's 10 000) | Appended during `epic-6033-forecasted-start-dates` DISTILL (2026-09-20), recording a mechanism the `DependencyAwareForecasting` fixtures already carried and generalising it to the HTTP host. Production picks a fresh starting number every run on purpose, so two unpinned runs over identical data return dates a day or so apart — a test asserting the day a Feature *starts* would be asserting sampling noise. The trial count is the other half: ten thousand runs buy precision no scenario needs, and paying for it per test makes an acceptance suite cost minutes. Note what the two doubles cannot do: `DrawsTheSameNumberEveryTime` collapses every percentile onto one day, so any claim about a *spread* — and any claim where two ways of computing a number would agree on a point mass — has to use the pinned sampler instead. |
| `ITeamMetricsService` (the measured throughput a forecast draws from) | `Mock<ITeamMetricsService>`, handing `GetForecastThroughputStatus` a `RunChartData` the test built with `RunChartDataGenerator` | Appended during `epic-6033-forecasted-start-dates` DISTILL (2026-09-20). **This is a driven-internal port deliberately faked, and the waiver is recorded in that feature's delta**: measured throughput is an *input* to a forecast rather than part of one, and seeding it as dated closed work items would put the metrics service's own windowing, filtering and blackout arithmetic between the number the test chose and the number the simulation drew — a scenario saying "three a day" would be asserting all of that too. | `ILighthouseClock` (what the instance believes the time is) | `FakeLighthouseClock` — a `FakeTimeProvider` behind the real `LighthouseClock`, so day and zone arithmetic stays production. `Clocks.SystemUtc` for the many places that have to hand something a clock but never read a moment off it | Appended during `epic-5511-task-manager` slice-03 DISTILL (2026-09-14), recording a mechanism already carried by seventeen files.
