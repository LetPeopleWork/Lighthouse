# ATDD Infrastructure Policy

Per `nw-distill` § Project Infrastructure Policy. One file per project. Apply-if-exists; write-if-absent; rewrite with `--policy=fresh`. Git history is the audit trail.

Bootstrapped during the `time-in-state-and-staleness` slice-03 DISTILL run (2026-05-25). This is a C#/.NET backend (`net10.0`) + React/TypeScript frontend + Playwright E2E project — NOT the Python/Hypothesis pilot. The Python-pilot artifacts (`tests/common/state_delta.<ext>`, `assert_state_delta` Universe assertions, Hypothesis/PBT harnesses, `__SCAFFOLD__` stubs) do NOT apply here; the C#/TS rows of the polyglot matrix govern (NUnit `[Ignore]` and Playwright `test.fixme` are the skip markers; backend ATs are black-box example-based via `WebApplicationFactory<Program>`). The mechanisms below were already encoded as precedent across slices 01–02 and are recorded here for the audit trail.

## Driving
| Port | Mechanism | Note |
|---|---|---|
| HTTP API (backend) | `WebApplicationFactory<Program>` (`TestWebApplicationFactory<Program>` + `WithTestAuthentication`) | Real ASP.NET host; `client.AsTeamAdmin` / `AsPortfolioAdmin` / `AsViewer` for RBAC. Routes are `/api/latest/...`. |
| Production React app (E2E) | Playwright against a locally-started app, Page Object Model only | No inline `page.locator` in specs. POMs in `tests/models/`. |
| Repository-invariant checks (`.github/scripts/*.mjs`) | `node:test` via the existing `Verify Workflow Scripts` job (`node --test .github/scripts/*.test.mjs`). The check is an exported function called directly: once against the real repository root for the end-state assertion, and once per seeded violation against a throwaway tree written to `mkdtemp` | Appended during `story-6070-toolchain-single-source` DISTILL (2026-09-25), following the precedent `generate-version.test.mjs` set. No `package.json` lives under `.github/scripts`, so these checks take no dependencies: YAML and Dockerfiles are read line by line, not parsed. The skip marker is `test(name, { skip: 'pending: …' }, fn)`. The real-repository assertion cannot be green at hand-off, because the repository *is* the thing being changed; the seeded-tree cases carry the behaviour. |
| React component tree (frontend ATs) | Vitest + React Testing Library, colocated `*.test.tsx`, rendered through the real component under test with `TerminologyContext` provided | No shallow rendering, no component mocking. Where a test needs the View Data path it renders `WidgetShell` with a `viewData` payload rather than reaching into `WorkItemsDialog` directly, so the payload contract is exercised. Appended during `story-5884-work-item-age-bands` DISTILL (2026-09-05), recording the mechanism already carried by roughly 3,200 lines of precedent in `WorkItemAgingChart.test.tsx`, `WorkItemsDialog.test.tsx` and `WidgetShell.test.tsx`. The skip marker is `it.skip` / `describe.skip`; a skipped test is still type-checked, so a component prop a pending test relies on has to exist before the suite can be green. |

## Driven internal (real)
| Port | Mechanism | Note |
|---|---|---|
| EF `LighthouseAppContext` + repositories (`IRepository<T>`, `IWorkItemStateTransitionRepository`) | Real EF context via the test factory; `Database.EnsureDeleted()` + `EnsureCreated()` per `[SetUp]` | Mirrors `ForecastFilter*IntegrationTest`. Sqlite + Postgres lockstep in CI. |
| Real Postgres (concurrency / migration-lock / shared-status-store ATs) | `Testcontainers.PostgreSql` — one container per test class, fresh DB; multi-replica simulated by N `WebApplicationFactory<Program>` hosts sharing the container's connection string | Added for `epic-5305-k8s-readiness` (slice-04 enabler, extended in slice-07). InMemory/SQLite **cannot** reproduce row-lock races, advisory-lock coordination, or concurrent `Database.Migrate()` — US-04 AC1 and US-07 AC1/AC3 require a real Postgres. Mark `[Category("requires-docker")]` so the suite can be filtered; CI runner provides Docker. |
| `IUsageDataConsentRepository` (one row per browser, keyed by token digest) | `Testcontainers.PostgreSql` — one container per test class, fresh DB; `[Category("requires-docker")]` | Appended during `epic-5733-opt-in-usage-data` DISTILL (2026-09-11), decided by the product owner. Revoke and the throttled liveness touch are **conditional updates read through their affected-row count** — the same shape `EmbedSessionSingleUseConcurrencyTests` needed a real provider for, and one EF InMemory cannot express at all. (Two other justifications originally given for this row were withdrawn on 2026-09-11: the `AppSetting.Key` dedup migration is unnecessary because `Key` is already the primary key, and the multi-replica heartbeat compare-and-swap has no store that can perform it yet — see ADR-174 point 8. This row stands on the consent store alone.) Note the cost, since it is wider than this row's precedent: `requires-docker` carries no `Integration` category, so **nothing filters it** — these run on every push (CI provides Docker) and need Docker locally. |
| Real Redis (SignalR backplane / distributed queue / shared status store ATs) | `Testcontainers.Redis` — one container per test class | Added for `epic-5305-k8s-readiness` (slice-07 enabler). Cross-pod SignalR fan-out (US-07 AC2) and the ADR-075/076 substrate need a real Redis backplane; in-memory cannot model cross-process delivery. `[Category("requires-docker")]`. |
| Seeded demo data (E2E) | `loadDemoScenario(request, scenarioId)` + `waitForBackgroundUpdates(request)` (POST `/api/latest/demo/scenarios/{id}/load`) | Deterministic seeded teams/portfolios/items with known states. PREFERRED over live connector syncs for walking-skeletons (live syncs flake on 0-WIP + overview Search hidden during active syncs). |
| `IFeatureOrdering` (Feature order, owned by epic #5375) | Real implementation via the test factory — **never mocked** | Appended during `epic-4365-dependencies` DISTILL (2026-08-17). The dependency warnings READ the total order to spot a blocker positioned below its dependent, and assert that nothing was reordered. Substituting the ordering would make "and Lighthouse has moved nothing" vacuous. Read-only in that epic; the writer stays epic #5375's. |
| `IForecastService` + `IRandomNumberService` — **real**, seed pinned (epic-boundary gold tests only) | Real Monte Carlo run against a fixed `IRandomNumberService` seed, executed twice: once with dependency data absent, once with it present, asserting every percentile identical | Appended during `epic-4365-dependencies` DISTILL (2026-08-17). This is the deliberate exception to the `Mock<IForecastService>` row below. A mocked forecast cannot prove "this epic moves no date" — the claim is precisely that the real simulation produces byte-identical output, so the simulation has to run. Confine to the `epic-boundary` scenarios; every other test in the epic keeps the mock. |
| `IUpdateStatusStore` (the record of which updates are in flight) — **real**, never mocked | Real store through the real `UpdateQueueService`: `InProcessUpdateStatusStore` by default, `RedisUpdateStatusStore` via `Testcontainers.Redis` under `[Category("requires-docker")]` for the shared-store scenario | Appended during `epic-5792-dependency-aware-forecasting` DISTILL (2026-08-21). Slice 00 debounces a forecast trigger behind the sibling Teams still queued, so "the trigger was parked" has to be a statement about the queue rather than about a mock. The Redis adapter runs only where Redis is configured, which is exactly why it needs a container rather than an assumption. |
| `IDomainEventDispatcher` + its registered handlers — **real**, never mocked | Real in-process dispatcher through the test factory; the observable is whatever the shipped handler drives | Appended during `story-5876-behaviour-settings` DISTILL (2026-08-31). "The policy change was published" is a claim about the fan-out reaching its handler, not about a call on a bus. Asserting it against a `Mock<IDomainEventDispatcher>` would keep passing after a handler is unregistered, which is the failure worth catching. |
| `IUsageDataEventQueue` (what an accepted batch waits in) + the hosted service that empties it — **real**, never mocked | Real queue through the real host. **The integration host removes every `IHostedService`**, so the drain does not run there: the scenario has to pull a trigger on the seam the controller writes to. Polling the outbound recorder is the fallback and costs every negative scenario its full budget | Appended during `epic-5733-opt-in-usage-data` DISTILL (2026-09-12, slice 01c). "The next event after a withdrawal did not happen" is a claim about what left the instance, and the check runs a second time on the way out of the queue — so a mocked queue would assert the accept half and silently drop the half that catches a withdrawal landing mid-flight. Nothing on this path is persisted, deliberately: a durable queue survives the withdrawal it is meant to obey. |

## Driven external / non-deterministic (fake)
| Port | Fake | Note |
|---|---|---|
| `ILicenseService` | `Mock<ILicenseService>` (`CanUsePremiumFeatures() → true`) | Injected via `RemoveAll` + `AddScoped` in the factory builder. |
| `IWorkTrackingConnector` (Jira / ADO / Linear / CSV) | `Mock<IWorkTrackingConnector>` for service-seam ATs; live connector sync only in E2E when unavoidable (deprecated for walking-skeletons in favour of demo data) | Service-seam ATs drive the REAL `WorkItemService` + real EF; only the connector boundary is faked. |
| `IDeliverySourceProvider` (reading the remote objects a Delivery binds its date to) | `Mock<IJiraWorkTrackingConnector>` registered in place of the real Jira connector — **never** `Mock<IWorkTrackingConnector>` | Appended during `epic-5565-delivery-date-sync` DELIVER (2026-08-23, slice 01a). The capability is declared on `IJiraWorkTrackingConnector`, and the controller decides whether a connection can offer sources by testing the resolved connector for `IDeliverySourceProvider`. A base-connector double fails that test, so every Jira scenario silently takes the "this tracker offers nothing" path and still passes. Only Jira is swapped: the real connector factory keeps resolving the production Azure DevOps, Linear, ServiceNow and CSV connectors, which is what makes "this tracker offers no delivery sources" a statement about shipped code rather than about a double. |
| `IForecastService` (Monte Carlo simulation) | `Mock<IForecastService>` injected via `RemoveAll` + `AddScoped` in the factory builder | Added during `blackout-day-forecast-shift` DISTILL (Epic 4974, 2026-06-05). The simulation is non-deterministic; for tests asserting a date/count *derived from* a forecast (not the simulation itself), pin the days value with a `WhenForecast` whose simulation mass sits on a single key so `GetProbability(p)` is fixed. The controller's settings-coupled `ITeamMetricsService.GetForecastThroughputStatus` is likewise stubbed when only the date/count projection is under test. |
| `IForecastUpdater` (the queue a forecast run is scheduled on) | `Mock<IForecastUpdater>` injected via `RemoveAll` + `AddSingleton` in the factory builder | Precedent from `epic-5375-manual-sorting`, recorded during `story-5876-behaviour-settings` DISTILL (2026-08-31). It is a background queue, so a scenario that waited for a run would be timing against a thread. Faking it turns "the change re-queues the forecasts" into something a test can see the moment the write commits — and it is the observable the real `IDomainEventDispatcher` row above is read through. |
| `IUsageDataPublisher` (the outbound call to the PostHog capture API) | A capturing fake registered in place of `PostHogUsageDataPublisher`, recording every payload it was handed | Appended during `epic-5733-opt-in-usage-data` DISTILL (2026-09-11). Emit is fire-and-forget and degrades silently by specification, so a real call would make "nothing was sent" indistinguishable from "the vendor was down". The fake is what turns the payload-purity and revocation-latency invariants into assertions. **A test may never let the real publisher resolve**: the collector host default is production, and a leaked emit lands in the census. The separate zero-leak assertion is the inverse — a `DelegatingHandler` over the named clients proving no request reaches the collector host at all when no browser has consented. |
| Every outbound HTTP request the application makes (the zero-leak observation) | `CapturedOutboundRequests` + `OutboundRequestRecordingFilter`, an `IHttpMessageHandlerBuilderFilter` registered on the test host. It sits in front of **every** client the framework hands out, records address and body, and answers locally so no test reaches a real network | Appended during `epic-5733-opt-in-usage-data` DISTILL (2026-09-12, slice 01c). A capturing fake publisher only proves the publisher was not called; this proves nothing left, whatever asked. It is exactly as complete as the rule that nothing on this path builds its own `HttpClient` — several elsewhere in this codebase already do, which is why the rule is scoped to the usage data path and why `UsageDataEmitSeamArchUnitTest` carries it. Without that rule the assertion decays into a tautology, so the two ship together or neither is worth having. |
| `IDrawStreamFactory` (where the feature forecast gets its random numbers) | `DrawsTheSameNumberEveryTime` when the claim is about *which day*; `DrawsFromAPinnedStartingNumber(seed)` when the claim needs a real spread. Registered by `RemoveAll` + `AddSingleton` in the factory builder, alongside a reduced `ForecastSimulationLimits` (50 runs deterministic, 1 000 sampled, against the product's 10 000) | Appended during `epic-6033-forecasted-start-dates` DISTILL (2026-09-20), recording a mechanism the `DependencyAwareForecasting` fixtures already carried and generalising it to the HTTP host. Production picks a fresh starting number every run on purpose, so two unpinned runs over identical data return dates a day or so apart — a test asserting the day a Feature *starts* would be asserting sampling noise. The trial count is the other half: ten thousand runs buy precision no scenario needs, and paying for it per test makes an acceptance suite cost minutes. Note what the two doubles cannot do: `DrawsTheSameNumberEveryTime` collapses every percentile onto one day, so any claim about a *spread* — and any claim where two ways of computing a number would agree on a point mass — has to use the pinned sampler instead. |
| `ITeamMetricsService` (the measured throughput a forecast draws from) | `Mock<ITeamMetricsService>`, handing `GetForecastThroughputStatus` a `RunChartData` the test built with `RunChartDataGenerator` | Appended during `epic-6033-forecasted-start-dates` DISTILL (2026-09-20). **This is a driven-internal port deliberately faked, and the waiver is recorded in that feature's delta**: measured throughput is an *input* to a forecast rather than part of one, and seeding it as dated closed work items would put the metrics service's own windowing, filtering and blackout arithmetic between the number the test chose and the number the simulation drew — a scenario saying "three a day" would be asserting all of that too. The fake therefore cannot model any of them, and no scenario using it may assert one. Where the windowing *is* the subject, `ForecastFilter*IntegrationTest` drives the real service and stays the precedent. |
| `ILighthouseClock` (what the instance believes the time is) | `FakeLighthouseClock` — a `FakeTimeProvider` behind the real `LighthouseClock`, so day and zone arithmetic stays production. `Clocks.SystemUtc` for the many places that have to hand something a clock but never read a moment off it | Appended during `epic-5511-task-manager` slice-03 DISTILL (2026-09-14), recording a mechanism already carried by seventeen files. Elapsed time asserted against the real wall clock can only ever say "greater than zero", which a stopwatch started at the wrong moment satisfies — so the whole slice-03 acceptance fixture pins the clock, through `TaskManagerAcceptanceTest.ConfigureAdditionalServices`. Note the scope: replacing `ILighthouseClock` freezes it for **everything** in that host, not just the code under test, so a fixture that also depends on time passing has to move the clock itself rather than wait. |
| `IForecastService.HowMany` read **per check** (a forecast whose four levels the scenario chose, for one sampling window over one horizon) | `ForecastWithScriptedChecks`, a decorator over the **production** `ForecastService` registered by `RemoveAll` + `AddScoped` in the factory builder: a check the scenario scripted gets a simulation whose 95/85/70/50 readings are exactly the scripted values (or an empty simulation, the engine's "no reading" case); every other forecast the application makes runs the shipped engine. `RunAsShipped()` hands the whole sweep back to the engine, with `DrawsFromAPinnedStartingNumber` and 1 000 simulated runs | Appended during `epic-4172-forecast-backtest-sweep` DISTILL (2026-09-26). A scenario about which confidence levels *held* has to choose what each check forecast, or it asserts sampling noise; and one real sweep costs about five seconds under CI's coverage run. A check is recognised by the length of the history it was handed and the days it forecast - nothing else about how the sweep calls the engine is assumed. The walking skeleton is the one scenario that runs the engine as shipped. |
